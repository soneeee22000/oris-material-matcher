# Why this project exists

A Bill of Quantities lists every material in a construction project, written by whoever priced the job, in their own words and often in French or English shorthand. To estimate a project's environmental impact, each of those lines has to be tied to one row of a reference material library, because that row carries the carbon factor. When a line is tied to the wrong row, nothing breaks: the report still renders, the total still adds up, and a wrong CO₂ factor is now silently attached to real tonnes of material.

That silence is what makes the error costly. A wrong match looks exactly like a right one, so it is only caught if someone rereads the line, and nobody rereads hundreds of lines per file. The mistake then travels into material comparisons, design choices and client reports, where it is much harder to trace back than it would have been to flag at the start. A line that is honestly marked "needs review" costs a minute of an analyst's time; a confident wrong match can cost the credibility of the whole assessment.

The people this matters to are the analysts who prepare impact assessments and the teams who rely on them. This project is built around their side of the trade-off: it matches a line only when the evidence is strong enough to be trusted, sends everything else to review with a reason and two suggestions, and never quietly drops a material as "not a material". Every decision can be explained after the fact, from the stored model calls, without calling a model again.

## Layer, problem, answer

| Layer                  | Problem it faces                                                                                                                                 | How the project answers it                                                                                                                                                                         |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Input parsing          | BoQ files mix section headers, empty rows and material lines, and a header mistaken for a material (or the reverse) corrupts everything after it | A structural header gate classifies headers from the shape of the row and the codes around it; any row that only looks like a header goes to review instead of being skipped                       |
| Library and enrichment | Library rows are terse, while BoQ lines are long, written in English or French and full of trade terms                                           | The whole library is shown to the model, never a shortlist that could miss the right row, and a bilingual enrichment adds a glossary of trade terms and their meanings to the library, each entry tagged with where it came from        |
| Two-pass model         | A single answer from a language model can be confidently wrong                                                                                   | Two passes over two different renderings of the library must agree, each quoting evidence from the line itself                                                                                     |
| Validators             | A model can invent a row id, cite text that is not in the line, or pick a parent row that is too generic                                         | Closed-world validators reject any answer that is not an existing row, whose evidence is not in the line, or whose attributes conflict with it                                                     |
| Threshold and verifier | Agreement alone still lets through confusions between sibling usages of the right material                                                       | A threshold frozen before the final evaluation decides what may be matched, and a sibling verifier re-asks about the nearest neighbouring rows before a match is accepted                          |
| Audit                  | A decision nobody can explain cannot be trusted or corrected                                                                                     | Every call is recorded with its prompt, raw response, cost and provider request id; `oris explain` reconstructs any line's decision and `oris replay` re-runs a whole run byte for byte at no cost |

## What this is not

- **Not a product deployment.** It is a take-home exercise: a CLI, an API, a local operator UI and committed outputs, not a service running behind a platform.
- **Scored on one project's BoQ.** The held-out lines come from the same project as the development lines, so the result says nothing yet about other projects or other writers.
- **The French library is certified by a smoke set, not a held-out bound.** It shows the operating point is safe on that taxonomy; it does not estimate precision there.
- **The UI is a local operator tool, added after submission.** `oris serve` serves it at `/ui` on this machine; it is not hosted anywhere, and in replay mode it shows recorded answers, not a model run. What it leaves out of [`ui-spec.md`](ui-spec.md) is listed in the [changelog](../CHANGELOG.md).
