This file lists every atomic requirement in the exercise brief (`docs/exercise-brief.md`). Each row gives the requirement, how I interpret it, the evidence that proves it, how that evidence is checked, and the `DESIGN.md` section that answers it. The phase gates in `DESIGN.md` §14 are checked against this table.

Status: pre-registration v2, merged before any model call. The tag `prereg-v1` (bc5c8a2) is the proof of v1. Rows changed in v2 end with the id of the amendment in `DESIGN.md` §16 that changed them, e.g. [A31]. [A30]

Count: 87 atomic requirements (`DESIGN.md` §16 A3). v2 changes rows in place; no row was added or removed, so the count stays 87. [A30]

Every row names the test or committed artifact that verifies it. `RQn` refers to the output checks in `docs/evaluation-protocol.md`, run by `check_requirements.py`.

## Ambiguities and the interpretation chosen

`DESIGN.md` §3.3 gives the decision for each of these.

- Coverage denominator: 'material lines' could mean the 252 labelled lines, the 265 material-bearing lines (252 plus 13 specialist material lines with no library equivalent) or all 282 L2 item rows. The GT cannot tell the 13 unmappable material lines apart from labour/service blanks, so ORIS's scorer on unseen data can most likely only use labelled lines. Proposal: 252 as the headline and 265 as a secondary figure, with the 13 identified by hand and the list committed.
- Specialist products with no library equivalent: the README groups them with headers, labour and services ('should stay blank'), but defines not_a_material as 'carries no material' and calls it an error to mark a material line not_a_material. The labels are blank either way. The decision should be needs_review, but ORIS's grader may expect not_a_material. State this and justify it in DESIGN.md.
- Blank subtype: 49 GT triples have a blank subtype and 70 global-library rows do too. Treat exact match including blank as correct, so emitting a blank where the GT has a specific subtype on a mixed parent (21 pairs, 80 rows) is wrong. The sample output emits blank subtypes for matched rows, which is consistent with this. Is there partial credit at the subtype level? We assume none for precision.
- needs_review label columns: the sample output leaves them blank. If a best-guess candidate goes into the canonical columns, ORIS's scorer might count it. Proposal: keep the canonical columns blank and put the guess in optional suggested_* columns.
- Precision scope: per language or pooled EN+FR? 'Both languages count' suggests each language must clear 90% separately. Also unclear whether the bar applies to the point estimate or the lower CI bound; with about 100 matched lines per language a Wilson lower bound of 90% needs a point estimate around 95%. Resolved in v2: per language; the lockbox reports both the point bar and the one-sided 95% Clopper–Pearson lower bound, and only that bound supports a 'certified' claim; dev selection uses a .95 bar per language. [A31]
- Latency definition: end-to-end wall-clock per file divided by lines (batching and concurrency allowed, as 'averaged, batching is fine' hints) versus mean per-call latency. Also, should header rows decided by rules at about 0 ms count in the average? Report both, with wall-clock over all rows as the headline and over L2 rows as secondary. Resolved in v2: the gate is wall-clock ÷ N_routed on a cold live run (RQ8); the per-line column follows the A45 attribution rule and is labelled 'attributed'. [A45]
- Cost scope: does it include retries, failed calls, the two-pass or abstention experiment calls, and the one-off offline enrichment? Do prompt-caching or batch-API discounts count as 'current API pricing'? Is the denominator 319 rows or 282 item rows? Pin a dated price table and report each variant. Resolved in v2: cache-write and cache-read rates are in the price table, the gate uses live runs with no cache hits, and replays copy source costs. [A45, A46]
- 'Accuracy at each hierarchy level': cumulative (type, type+usage, triple) or independent per level? Usage strings repeat across types, so independent usage accuracy means little. Denominator: matched rows (conditional precision) or all labelled rows (coverage-style)? Report both.
- 'Share of lines per decision': over all 319 rows (including 37 trivially not_a_material headers) or L2 rows only? Headers inflate not_a_material and the cost/latency denominators.
- Scorer genericity: the join key is presumably Item No. ORIS's reference for the unseen BoQ might use a different key column name, contain duplicate Item Nos, or lack decision semantics (the reference has labels only). Should the scorer accept a --key option and column-name mapping? Should it infer 'material line' as 'has labels'? Resolved in v2: key auto-detection plus `--key`, label-column aliases, (key, occurrence) joins with a duplicate warning, labels-only references accepted, and `--strict` only for our own files. [A34]
- API library selection: per-request parameter, server start-up config, or library upload? The README only says CLI selectable 'via an option' and the API exposes 'the same logic'. Resolved in v2: a library id from Settings.libraries per request; clients never send paths. [A51]
- 'Any BoQ file with the same columns': does that cover column order differences, extra columns, Excel input for the CLI (the README only mentions Excel for the UI), or other encodings? Proposal: CSV and XLSX in the CLI and UI, columns by name, UTF-8 with a BOM tolerated. v2: a cp1252 fallback with a warning when UTF-8 fails, and structural header detection for other numbering schemes. [A15, A48]
- Live session with the French library: the GT has 0 triples in the FR library, so precision on the FR library cannot be measured except through the ~25-line hand-labelled smoke set. Is enrichment of the FR library expected ahead of time, or must enrichment of a possibly different library also run live inside the budget? v2: enrichment and policy are keyed by library_sha256; an unknown library runs unenriched under the strictest policy with a logged warning. [A38]
- Model-size list names 'Claude Haiku' without a version. We assume Haiku 4.5 qualifies. Resolved in v2: an enforced allowlist (`claude-haiku-*`, `gpt-4o-mini*`, `gemini-*-flash*`, `local:≤8B`) and no non-small model anywhere, fallback included [A33]. Also unclear whether local embedding or reranker models count toward 'mixing models' or the ≤8B limit (assume yes for ≤8B, $0).
- Design document timing and content: the questions are forward-looking ('what will you try first'), which supports the pre-registration approach. The rubric also expects results (baseline delta, confidence). Is a separate DESIGN.md from the README expected, or can sections be merged? Plan: DESIGN.md pre-registration plus dated results sections.
- Raw response for rule-decided lines (the G1 header gate) and for replayed or cached runs: what counts as 'raw response', 'model' and 'latency' when no LLM was called? Proposal: model='rules', raw_response=null, cost=0, plus a cache-hit flag for replays. v2: rule rows are 0.000000 / 0 / rules with empty call_ids; replay and cache hits copy the source cost and latency and set cache_hit and source_call_id. [A45]
- Labour-and-supply lines (e.g. 'supply and lay', 'cut, bent and fixed') carry both labour and material. The README lists labour as non-material, but the sample matches 'Reinforcing steel B500B, cut and bent'. The decision boundary rule needs stating.
- EN/FR consistency: since both files describe the same project, is disagreement between EN and FR decisions for the same Item No. an error ORIS cares about, or a legitimate abstention signal we may use? Using the other language's output at inference could count as cross-input leakage and must be disclosed if used.
- AI tools policy: assistants are welcome. The README states how they were used if relevant; evaluation evidence never depends on them.
- UI scope: the brief says 'minimal'. I aim for a polished but simple single page, which is optional and must not cost evaluation time. It is built after the eval-freeze, both outputs and the clean-clone check, as deferred work after the must-haves. [A14, A32]
- Deadline: 'one week from receipt' versus the stated Fri 9 Oct 17:00 Paris. We assume the latter is authoritative.
