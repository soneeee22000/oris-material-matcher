## 7. Observations

Each observation gives what was seen, what it means, which part of the design handles it, and when it is verified.

### O1 · B2 matched a service line as a material (a match on a blank-labelled line)

- **Seen:** B2 smoke run `20261005T143000Z-d657c790`, item `00.01.0030.` "Demobilise and reinstate compound areas", priced in LS, labelled blank (a service) in the ground truth. Haiku answered `kind: material`, top1 `T13.U01.S05` → `Construction and demolition material / 17 01 – Concrete, bricks, tiles and ceramics / 17 01 07 – Mixtures …`, confidence 75, gap `clear`, evidence "Remove temporary facilities, break out compound hardstanding".
- **Meaning:** a false positive of the B2 baseline. In the §10.7 taxonomy it is kind `match_on_blank`, likely cause `gt_convention`: breaking out hardstanding does produce C&D waste, but this dataset labels site-establishment lines as services. B2 matches every valid answer by design (§10.5), and §7.1 step 3 pre-registers the hypothesis that B2's matches are not ≥ .90 precise without abstention. This line is an instance of that hypothesis.
- **Handled by:** four independent B3 checks, any one of which sends the line to `needs_review` at the strictest threshold:
  1. Confidence 75 is in the 70–79 bucket.
  2. k = 2 passes over two renderings must agree.
  3. No hard attribute is stated, so signal (b) is `no_evidence`, not `agree`.
  4. The G2 service gate cannot skip it, because the model said "material".

  The result would be `LOW_SIGNAL`.

- **Verified:** not yet. The §10.6 selection loosens the threshold as far as dev precision ≥ .95 allows, so a line like this could be matched at a looser threshold. It is checked in G2, on the B3 dev run and in `eval/errors_dev.csv`.

### O2 · An FR run scored against the wrong library (operator error, now invalid)

- **Seen:** run `20261005T144432Z-6e8ed5f6` (ledger id `B2-slice40-fr`, first row) used `data/oris_materials_fr.csv`. Matched precision was 0/26.
- **Meaning:** the ground truth holds global-library strings, and the FR library shares no triple with it, so this run cannot score anything. The scored FR configuration is the FR input with the **global** library, as B1 and the brief's .159 figure use. The FR library is evaluated only through the hand-labelled smoke set (G3). The run is invalid; it cost $0.160.
- **Handled by:** the ledger is append-only, so the row stays and is marked invalid here. The rerun is `20261005T144524Z-f2fd2efa` (ledger id `B2-slice40-fr`, second row). Engineering fix, ticket G1-T1b: the runner refuses to score when none of the reference triples is a row of the selected library.
- **Verified:** after the fix, a test shows that the FR library with the GT reference is refused.

### O3 · The cached library prefix was written 5 times in one run

- **Seen:** EN slice run `20261005T144408Z-72765ec5`: cache write 57,780 tokens = 5 × 11,556, cache read 358,236, over 36 calls. Batch 1 went alone, as §11.3 says.
- **Meaning:** four of the concurrent calls that followed the solo call still wrote the cache instead of reading it. Each extra write costs about 11.6k × ($1.25 − $0.10)/M ≈ $0.013, so about $0.05 per cold run. The FR run right after it read the warm cache with 0 writes.
- **Handled by:** an open engineering question for G3, where the cold-run cost and latency are measured (§11.3 concurrency, A46).
- **Verified:** G3 cold run.

### O4 · French evidence quotes exceed the 12-word cap, and correct answers are lost

- **Seen:** FR slice run `20261005T144524Z-f2fd2efa`: 4 of 40 lines became `LLM_FAILURE:malformed`. All 4 were well-formed answers whose `evidence` was 14 or more words, for example "Maçonnerie porteuse en terre cuite triée séparément, évacuée sous code déchet 17 01 02". The rejected answers include a correct one (`01.02.0020.`, top1 = Bricks, which matches the ground truth). EN: 0 of 40.
- **Meaning:** the v1 schema caps evidence at 12 words (§9.4), and the validator applies that cap strictly (W1 review fix). French phrasing is longer, so the cap costs French recall.
- **Handled by:** §10.9 pre-registers the remedy: "if [the evidence check] rejects more than 3 correct matches, the evidence length is widened and the prompt version bumped (logged)". This is a G2 decision on the full dev runs, and it is logged as an experiment.
- **Verified:** G2, by counting correct answers rejected for evidence length on all dev lines.

### O5 · One invalid line rejected the whole batch

- **Seen (code):** `llm/wrapper.py` `_validated_lines` validates `BatchAnswer` as one object. A single line that fails validation, for example on evidence length, makes the whole batch `malformed`. The batch is then bisected and every half re-asked, which throws away the valid answers of the other lines.
- **Meaning:** wasted spend and latency on full batches of 10, and lines that share a batch with an offender get re-asked for no reason. The O4 slice runs did not show this, because their batches had one line each.
- **Handled by:** engineering fix, ticket G1-T1a, before the full dev runs. The envelope is validated once, and each line object is validated on its own. Valid lines are accepted. An invalid line is failed as `malformed` with its raw JSON kept, and other lines are never re-asked because of it. §11.3's bisection still applies when the envelope itself is broken (truncation or invalid JSON).
- **Verified:** a fault-matrix test where 1 of 10 lines breaks the evidence cap gives 9 accepted lines, 1 `malformed` line and no extra calls.

### O6 · The FR library is too small to cache

- **Seen:** `oris doctor --live`: the global library renders to 9,553 tokens (cacheable). The FR library renders to 3,380 tokens, below Haiku 4.5's minimum cacheable length.
- **Meaning:** a live run on the FR library pays the full input price on every call. At this size that is about $0.0034 per call, which is still within the cost target. This matters for the live session, which uses the FR library.
- **Verified:** G3 FR smoke-set run, for cost per 100 lines on the FR library.

### O7 · The rate-limit tier is high

- **Seen:** the doctor recorded tier `custom (above tier 4)` from the `anthropic-ratelimit-*` headers (`evidence/doctor_2026-10-05.json`).
- **Meaning:** the A39 rule (move up a tier before G4 if the projected cold run exceeds 2 s per line) does not bind at this tier.

### O8 · Process: an interrupted workflow and a bad relaunch

- **Seen:** the laptop shut down during W3. On resume, the cached agents replayed, but the live fixer read its prompt as a status question and changed nothing. The next fix launch passed a placeholder string instead of the findings list; it was stopped within seconds and relaunched.
- **Meaning:** about 2 minutes of agent time lost, no API spend. Fix prompts now state that the task is to edit code, and workflow inputs are checked before launch.

### O9 · Process: the blueprint hero ran ahead of the code

- **Seen:** the 3D hero showed "first batch alone, then 4 batches at a time" and a streaming pipeline. `MatchService` actually does: batch 1 of each pass alone; then 82 calls with at most 4 in flight, all of pass 1 before pass 2; deciding only after every call returns; one write in input order.
- **Handled by:** the hero was rebuilt from the service's real stages, and an automated schedule check asserts each rule. A standing rule now applies: visuals are checked against the code, or labelled as spec or illustrative.
