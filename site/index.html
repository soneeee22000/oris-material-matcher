ORIS material matcher

    02 · Problem and objective

    A wrong match is worse than no match

    Each library row carries its own CO₂ factor. A valid-looking but wrong row silently attaches the wrong number to a client's project. So precision is the constraint and coverage is what gets maximised: anything uncertain goes to an engineer, with a reason and two suggestions.

    Correct match
    Filled automatically. This is the time saving.
    Needs review on a material line
    An engineer confirms or corrects it, helped by a pre-filled top-2 suggestion.
    Wrong match
    The wrong CO₂ factor reaches the project. The 90% precision bar guards against it.
    A material skipped as "not a material"
    The material disappears without trace. Target zero, enforced by construction.
    Header or service skipped
    Correct; nothing is lost.

    The objective, written as an optimisation

    maximise match coverage
    subject to
      precision(matched) ≥ 0.90 per language
      materials decided not_a_material = 0
      cost ≤ $2 / 100 lines
      mean latency ≤ 2 s / line
      every emitted row ∈ loaded library

    These were the brief's constraints and were fixed before any model call. The design, the evaluation protocol and the frozen dev/lockbox split were committed as tag prereg-v1; the lockbox was then scored once, at tag eval-freeze.

    Out of scope: PDF BoQs, editing decisions in a UI, multi-tenant authentication, model training.

    03 · Data understanding

    One project, two languages, one synthetic sweep of the library

    The English and French BoQs are the same project, line for line. Their labels touch – of the – global-library rows, and – of those rows are used by exactly one line, so any example taken from the labels would leak its own answer. The matcher uses none.

The French library is a different taxonomy and shares no labelled row.

    Usage is the hard level, and lexical matching cannot carry French

    On dev, the TF-IDF baseline (B1) at its best threshold matched – precision in English and covered – of labelled lines; in French it covered only –. The French BoQ is a localised rewrite of the English one, not a translation, and it shares almost no words with the English-language library its labels use.

    AC → GB / BBSG RA → AE WMA → "tiède" crushed stone → GNT Ready-mix → BPE binder 50/70 → 35/50 "couche de fondation" = sub-base

    Confusers seen in the data

    piers vs piles base vs binder course base layer vs sub-base quick vs slow visco-elastic pile caps → footings segmental rings: tunnel concrete vs precast "RC" = recycled concrete or rock class PCE → plasticiser

    These are usage confusions inside the right material type. They are where a wrong-but-valid match is most likely, and they are what the sibling verifier (E-08) was added for. Both lockbox errors are of this kind.

    Labelled lines by material type and project section

    Surprises that shaped the design

    1. The labels are a synthetic sweep: about one line per library leaf. Examples from the labels would teach answers, not skills, so prompts hold only the library, its enrichment and a sourced glossary.
    2. No lexical score is a usable confidence signal. Confidence has to come from complementary checks: agreement of two passes, attribute agreement, and the model's own bucket.
    3. Some blank-labelled lines carry real materials with no library row (bearings, membranes, drains). They must go to review, never to "not a material".
    4. Top-level headers are bare digits (0 to 9). A header test shaped NN. would miss all ten, so the header gate is structural.
    5. Two diameter characters and two decimal conventions (∅ and Ø; decimal comma and dot). Normalisation is for matching only; output strings stay verbatim.

    Label conventions followed, not "fixed"

    • All in-situ building lines in section 09.01 are labelled General Ready mixed.
    • Precast sleepers sit under Prefab, although the same usage string exists under Concrete.
    • Limestone filler maps to Limestone / for all usage, not Filler.
    • Lines starting with an activity verb ("Break out", "Dredge") are materials (waste, spoil), not services.
    • Canonical labels keep their trailing spaces; strings are compared exactly.

    No item-specific rule encodes any of them. Source: docs/data-analysis.md.

    04 · How it works

    A pure core, swappable edges

    Parsing, matching, validation and decision logic are separate modules. The domain does no I/O, so every rule is unit-testable and a recorded run can be re-decided without calling the API. The CLI and the API drive the same MatchService.

      08 · Engineering

      Every failure ends in review, never in a lost line

      Whatever happens, the output keeps the input's length and order, and every affected line goes to review with its failure code. Every line and every API attempt leaves a record.

      Failure handling

      • Adapters never raise for API failures; one wrapper owns retries, the budget, cost, recording and the response cache.
      • Timeouts, rate limits, overloads, truncation, refusals, malformed or missing answers end as needs_review with LLM_FAILURE:<kind>, LLM_UNAVAILABLE or BUDGET_CAP (rule D1).
      • A missing pass never becomes a low-signal guess: LLM_FAILURE:partial_signal (D1b).
      • The first batch of a run goes alone so the prompt cache is written once; the rest fan out under a fixed concurrency limit.
      • If the primary model is unreachable, gpt-4o-mini takes over at the strictest threshold, because it was not certified.

      The audit trail, per line

      • manifest.json: requested and served model, library SHA-256, prompt version, enrichment and config hashes, policy and its resolution, code SHA with a dirty flag, split SHA, spend.
      • calls.jsonl: one record per attempt with OTel GenAI field names (gen_ai.*), request SHA-256, provider request id, HTTP status, usage, cost, latency.
      • audit.jsonl: one record per line with the rule that fired, the reason, the signals, top-2, the attribute result, the line's raw response and its call ids.
      • The output CSV carries the decision, the three labels, the reason, model, prompt version, attributed cost and latency, and two suggestions in separate columns.

      API (FastAPI)

      POST /v1/match   a JSON list of lines → one decision per line
                 more than 500 lines → 413; unknown fields → 422
GET  /health     liveness
GET  /ready      readiness, with no model call

      A model failure never causes a 5xx: the response is a 200 with every line present and a per-line reason. An optional bearer token (ORIS_API_TOKEN) guards /v1/*. Each match writes the same run folder as the CLI. GET /v1/diagnostics/llm and the async /v1/jobs routes are designed in DESIGN.md but not built.

      CLI (Typer)

      • oris match (the default): the brief's command, CSV in, CSV out.
      • oris demo: replays the committed lockbox runs and checks them byte for byte against the outputs, at $0 and without a key.
      • oris explain: why a line got its decision, from the run folder only.
      • oris replay: re-decides a recorded run from calls.jsonl, with no API call.
      • oris score, oris select and oris doctor: the scorer, the threshold selection rule and the environment check.

      CI, on Linux and Windows, offline

      ruff check and format mypy --strict pytest, live tests excluded coverage ≥ 80% on the domain and the service clean-clone rules-only run, RQ1–RQ5 RQ11: lockbox outputs replay byte-identical this page's data.json is current

      Tests use a fake LLM with fault injection and the replay adapter; nothing in CI needs a key. See .github/workflows/ci.yml.

      10 · Limitations

      Known weaknesses, and what comes next

      Known weaknesses

      • French coverage pays for French precision. Lockbox coverage is – in French against – in English. Declined lines go to review with a reason and two suggestions, never to a wrong match.
      • Usage confusions inside the right type survive. Both lockbox errors are of this kind: railway sub-ballast matched to ballast aggregates, and French couche de fondation (sub-base) matched to the base layer. The verifier reduces this class; it does not remove it.
      • The verifier costs coverage once the enrichment is in place. It was kept because dropping it was not registered before that comparison was seen.
      • The French library is certified by a smoke set, not a held-out measurement (chapter 07).
      • The fallback model is not certified. If the primary is unreachable, gpt-4o-mini decides at the strictest threshold and almost every line goes to review.
      • The lockbox is a same-project holdout. It was blind to tuning, not to the data exploration done before the split. The unseen live BoQ is the only fully blind test.
      • Not built: the hybrid retriever for large libraries, a local ≤ 8B model adapter and the LLM diagnostics endpoint. The operator UI (oris serve, /ui) was added after submission and is partial: no custom library upload. The triggered header_context arm was not run before the freeze.

      With more time

      • Run the header_context arm, and label a held-out French-to-French set large enough to bound precision on the French library.
      • Register and measure "verifier off, given the enrichment" blind, on fresh votes.
      • A carbon-weighted error metric once ORIS CO₂ factors are available, so a wrong match is weighted by the size of the carbon mistake.
      • The deferred hardening: the full fault matrix with a 429 storm, CLI/API parity over whole files, and the doctor measuring the enriched prompt for budget reservations.
      • Build the hybrid retriever and measure its recall for libraries above the whole-library size limit; add and benchmark a local ≤ 8B adapter.
      • Finish the operator UI: custom library upload and an axe contrast pass (docs/ui-spec.md).
